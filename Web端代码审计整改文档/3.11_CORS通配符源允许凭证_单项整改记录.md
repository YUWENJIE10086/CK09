# 3.11 单项整改记录：CORS 通配符源 + 允许凭证

## 一、原审计项
- 原报告编号：3.11
- 风险等级：高风险
- 原问题：CORS 使用通配符 Origin，同时允许携带凭证，可能使不可信站点发起跨域凭证请求。
- 原报告修复方向：禁止任意 Origin，改为明确可信域名白名单，并避免多处 CORS 配置冲突。

## 二、代码核验
实际核验文件：
- `Traeppp09/ruoyi-barn/src/main/java/com/barn/common/security/SecurityConfig.java`
- `Traeppp09/ruoyi-barn/src/main/java/com/barn/common/config/WebMvcConfig.java`
- `Traeppp09/ruoyi-barn/src/main/resources/application.yml`

整改前确认存在两套重复宽松配置：
1. SecurityConfig：`setAllowedOriginPatterns("*")` + `setAllowCredentials(true)`
2. WebMvcConfig：`allowedOriginPatterns("*")` + `allowCredentials(true)`

因此原报告 3.11 问题真实存在。

## 三、实际整改
### SecurityConfig
- 删除任意 Origin pattern；
- CORS Origin 改为显式白名单 `setAllowedOrigins(origins)`；
- 白名单来自 `security.cors.allowed-origins`；
- 对配置值执行 trim、去空值，并明确过滤 `*`；
- 如果过滤后没有任何可信 Origin，应用启动失败，避免错误配置时自动降级成开放策略；
- HTTP Method 收口为 GET/POST/PUT/DELETE/PATCH/OPTIONS；
- Header 收口为 Authorization、Content-Type、X-Requested-With、Accept、Origin；
- 保留凭证模式，但仅对显式可信 Origin 生效。

### WebMvcConfig
删除重复的 `addCorsMappings` CORS 配置，仅保留静态资源映射。CORS 统一由 Spring Security 的 `CorsConfigurationSource` 管理，避免两套策略互相覆盖。

### application.yml
新增：
`security.cors.allowed-origins: ${CORS_ALLOWED_ORIGINS:http://localhost:8080,http://localhost:5173}`

开发默认仅允许本机前端地址；生产环境必须通过 `CORS_ALLOWED_ORIGINS` 指定实际可信前端域名，多个 Origin 用逗号分隔。

## 四、静态复核结果
整改后逐文件复查：
- SecurityConfig 不再存在 `setAllowedOriginPatterns`；
- WebMvcConfig 不再存在 `addCorsMappings`；
- Java Web 配置不再存在 `allowedOriginPatterns("*")`；
- `allowCredentials(true)` 仅与显式 `setAllowedOrigins(origins)` 配合；
- 通配符 `*` 不会进入最终 Origin 白名单；
- CORS_ALLOWED_ORIGINS 已配置化。

## 六、当前结论
状态：已完成代码整改并通过本轮静态复核。

原 3.11 的攻击条件“任意 Origin + credentials”已被消除。审计复测时建议分别使用白名单 Origin 与恶意 Origin 发起预检/实际请求，确认仅白名单 Origin 返回匹配的 Access-Control-Allow-Origin，恶意 Origin 不获得跨域授权。
