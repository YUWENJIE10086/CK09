# 3.16 单项整改记录：缺少 RBAC / 所有用户统一 ROLE_USER

## 一、原审计项
- 原报告编号：3.16
- 风险等级：高风险
- 原问题：JWT 认证后所有用户统一被赋予 `ROLE_USER`，没有依据账户角色区分权限，导致“已认证”基本等同于可访问全部受认证保护接口。
- 原报告修复方向：建立真实角色来源，将角色写入/关联认证上下文，并对敏感管理接口实施角色授权。

## 二、代码核验
涉及：
- `JwtUtil.java`
- `JwtAuthenticationFilter.java`
- `LoginController.java`
- `SecurityConfig.java`
- `SysUser.userType`

整改前 JwtAuthenticationFilter 固定执行：
`new SimpleGrantedAuthority("ROLE_USER")`

无论数据库 `userType` 是什么，Spring Security 中所有已认证用户 Authority 完全相同。与此同时绝大多数路由仅使用 `.anyRequest().authenticated()`，没有角色边界。原报告 3.16 问题真实存在。

## 三、角色来源设计
仓库现有 SysUser 已有 `userType` 字段，登录响应也会向前端返回 userType，因此本次不新增另一套角色表，而是复用数据库 userType 作为角色来源。

当前仓库未发现明确、统一的 userType 枚举定义，因此本次不凭空定义完整业务角色权限矩阵。管理员兼容现有常见值：
- admin
- 00
- 0

上述值映射为 `ROLE_ADMIN`。其他非空 userType 规范化为独立的 `ROLE_<USERTYPE>`，不再全部固定为 ROLE_USER；空值兼容为 ROLE_USER。

## 四、实际整改
### 1. JwtUtil
`generateToken` 增加 userType 参数，并写入 JWT claim：
`claims.put("userType", userType)`

### 2. LoginController
登录签发 Token 时传入：
`user.getUserType()`

### 3. JwtAuthenticationFilter
取消固定 `ROLE_USER`。

认证时仍根据 JWT userName 重新查询数据库用户，并：
- 要求用户存在；
- 要求 status == "0"；
- 使用数据库当前 `user.getUserType()` 调用 `resolveRole`；
- 将结果写入 Spring Security Authentication Authority。

特别说明：权限判断以“数据库当前 userType”为准，而不是直接信任 JWT 中旧的 userType claim。这样账户角色被调整或账户被停用后，旧 Token 不会继续保留旧角色权限。

### 4. SecurityConfig
对敏感用户管理接口增加：
`.antMatchers("/system/user/**").hasRole("ADMIN")`

同时发现 `/system/user/updatePwd` 是所有登录用户的“修改自己密码”入口。若整个路径直接 ADMIN-only 会误伤普通用户，因此按 Spring Security 匹配顺序在管理员规则之前增加：
`.antMatchers("/system/user/updatePwd").authenticated()`

最终效果：
- 自助修改自己密码：任意已认证有效用户；
- 用户列表/详情/新增/修改/删除/管理员重置密码/状态修改：ROLE_ADMIN；
- 其他业务接口暂保持 authenticated，不在缺乏业务角色矩阵证据时擅自全部改为 ADMIN。

## 五、静态复核
- JwtAuthenticationFilter 固定 `new SimpleGrantedAuthority("ROLE_USER")`：已删除；
- Authority 来源于数据库 userType：是；
- 停用用户不建立认证上下文：是；
- JWT 含 userType claim：是；
- 登录签发传入 userType：是；
- `/system/user/updatePwd`：authenticated；
- 其余 `/system/user/**`：hasRole("ADMIN")。

## 六、安全边界与后续
本项建立了可工作的 RBAC 基础和首个明确的敏感管理边界，但仓库没有提供完整“业务角色—Controller—操作”权限矩阵，因此没有武断地把烤房、维修、资金、算法等 18+ Controller 全部标记 ADMIN。若业务制度已有管理员/技术员/普通用户等权限表，应在此 RBAC 基础上继续细化 URL 或方法级权限。

这比“所有 Controller 一刀切 ADMIN”更符合最小破坏原则，也避免正常业务角色被全部拒绝。

## 八、当前结论
状态：已完成原报告 3.16 核心整改并通过本轮静态复核。

原攻击条件“所有认证用户均为 ROLE_USER、敏感用户管理接口没有角色区分”已消除。审计复测建议至少准备管理员和普通用户两个账户，验证普通用户可修改自己的密码但无法访问用户列表、新增、编辑、删除、重置他人密码和状态修改；管理员应按预期具备上述管理权限。
