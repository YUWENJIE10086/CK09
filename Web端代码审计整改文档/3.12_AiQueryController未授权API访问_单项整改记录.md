# 3.12 单项整改记录：AiQueryController 未授权 API 访问

## 一、原审计项
- 原报告编号：3.12
- 风险等级：高风险
- 原问题：`AiQueryController` 全部接口被 SecurityConfig 配置为 `permitAll`，未认证访问者可直接查询烤房业务数据。
- 原报告修复方向：取消匿名放行，对 AI 查询接口实施身份认证/访问控制。

## 二、代码核验
涉及文件：
- `Traeppp09/ruoyi-barn/src/main/java/com/barn/common/security/SecurityConfig.java`
- `Traeppp09/ruoyi-barn/src/main/java/com/barn/barn/controller/AiQueryController.java`

整改前 SecurityConfig 明确存在：
`.antMatchers("/barn/ai-query/**").permitAll()`

AiQueryController 本身包含 4 个 GET 查询接口，且无独立认证约束，可查询烤房列表、详细信息、县级统计和全局概览。详细接口涉及地址、经纬度、技术员、健康分、剩余寿命等业务数据。因此原报告 3.12 问题真实存在。

## 三、实际整改
删除 SecurityConfig 中：
`.antMatchers("/barn/ai-query/**").permitAll()`

删除后，`/barn/ai-query/**` 自动落入现有：
`.anyRequest().authenticated()`

项目现有 JwtAuthenticationFilter 会解析 `Authorization: Bearer <JWT>`，只有有效 JWT 对应的现存用户才会建立 Spring Security Authentication；未认证请求由现有 AuthenticationEntryPoint 返回 HTTP 401。

本项没有提前把 AiQueryController 强制设置为 ADMIN。原因是原审计项 3.12 的问题是“匿名未授权访问”，而项目当前角色体系本身将在 3.16 单独整改。此处先完成身份认证边界，避免把 3.16 的 RBAC 问题混入本项并造成正常业务用户误封。

## 四、Dify 调用兼容说明
AiQueryController 注释说明该接口同时供 Dify 工作流 HTTP 节点调用。整改后 Dify 不再允许匿名调用，必须携带有效的系统认证凭据。当前仓库没有成熟的服务间 API Key/机器身份机制，因此本项没有自行新增硬编码共享密钥，以免引入新的凭据风险。

后续如业务要求 Dify 使用独立机器身份，应单独实现可轮换、可撤销、最小权限的服务凭据，而不是重新开放 permitAll。

## 五、静态复核
整改后复核：
- `/barn/ai-query/**.permitAll()`：0 处；
- SecurityConfig 保留 `.anyRequest().authenticated()`；
- AiQueryController：4 个 HTTP 查询接口；
- Controller 内不存在额外匿名放行标记。

攻击链变化：
整改前：匿名请求 -> permitAll -> AiQueryController -> 数据库查询 -> 返回业务数据。
整改后：匿名请求 -> Spring Security -> 401；有效 JWT -> 认证成功 -> AiQueryController。
