# 3.13 单项整改记录：ImageController 路径穿越

## 一、原审计项
- 原报告编号：3.13
- 风险等级：高风险
- 原问题：`ImageController.resolveOriginalFile` 未防护 `../` 等路径穿越，用户可控 path 直接参与本地文件路径构造。
- 原报告修复方向：规范化目标路径并验证其必须位于允许的上传根目录内，禁止目录逃逸。

## 二、代码核验
整改文件：
`Traeppp09/ruoyi-barn/src/main/java/com/barn/barn/controller/ImageController.java`

整改前逻辑最终执行：
`return new File(basePath + cleaned);`

虽然代码会去除前导斜杠和 `upload/` 前缀，但没有对 `..` 路径段进行规范化后的根目录校验，因此 `../`、混合路径分隔符等输入可使目标文件逃出 upload.path。原报告问题真实存在。

## 三、实际整改
1. 使用 `Path / Paths` 替代字符串路径拼接；
2. 将 upload.path 转换为绝对规范化根路径：
   `Paths.get(uploadPath).toAbsolutePath().normalize()`
3. 用户相对路径经 `resolve(...).normalize()` 后得到目标路径；
4. 使用 `resolved.startsWith(uploadRoot)` 做路径段级根目录约束；
5. 目标等于根目录本身时拒绝；
6. 拒绝绝对路径；
7. 拒绝 NUL 字符；
8. 将反斜杠统一转换为正斜杠，避免 Windows/Unix 混合分隔符绕过；
9. 增加图片扩展名白名单，仅允许 jpg/jpeg/png/gif/webp/bmp，避免缩略图接口退化为任意文件读取器；
10. 外部 http/https URL 继续拒绝。

## 四、复核
整改后关键安全链路：
`request path -> 清理 -> 分隔符统一 -> 相对 Path -> 扩展名白名单 -> uploadRoot.resolve -> normalize -> startsWith(uploadRoot) -> File`

已确认：
- 原 `new File(basePath + cleaned)` 拼接逻辑已删除；
- 存在 NUL 拒绝；
- 存在反斜杠统一；
- 存在 `toAbsolutePath().normalize()`；
- 存在 `resolve(relativePath).normalize()`；
- 存在 `resolved.startsWith(uploadRoot)` 根目录校验；
- 存在图片扩展名白名单。

典型攻击输入如 `../secret.jpg`、`../../etc/passwd`、`..\\..\\secret.jpg` 经规范化后不能通过根目录约束；非图片扩展名即使位于上传目录也不会由该缩略图接口读取。

## 五、关于 /api/image/** 匿名访问
SecurityConfig 当前仍对 `/api/image/**` 和 `/upload/**` 配置 permitAll。这属于资源访问控制策略，与本项“路径穿越导致目录逃逸”是不同问题。本次 3.13 不擅自改变现有图片公开访问业务语义；整改后的 path 即使匿名可调用，也只能解析到 upload.path 内允许的图片文件。

如审计范围要求图片本身也必须鉴权，应作为独立访问控制项进一步收口，而不是把它混同为路径穿越修复。
