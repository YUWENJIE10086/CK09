# 3.10 单项整改记录：HealthAlgoController 动态列名 SQL 注入

## 一、原审计项
- 原报告编号：3.10
- 风险等级：高风险
- 原问题：HealthAlgoController 的 algo 参数参与 SQL 列名拼接，攻击者可构造恶意 SQL 标识符造成 SQL 注入。
- 原报告修复方向：对可变列名实施严格白名单，不允许未经验证的用户输入直接进入 SQL。

## 二、代码核验
整改文件：
`Traeppp09/ruoyi-barn/src/main/java/com/barn/barn/controller/HealthAlgoController.java`

核验发现报告问题真实存在，而且同一控制器存在多个同类入口：
- 健康算法 apply：`health_ + algo` 用于 UPDATE 列名；
- 健康算法 list：动态列名用于 SELECT / ORDER BY；
- 健康算法 stats：动态列名用于 COUNT / AVG / MIN / MAX / CASE；
- 寿命算法 life-apply / life-list / life-stats 同样存在 `life_ + algo` 的同类动态列名问题。

## 三、实际整改
新增服务端固定白名单：
- bmhi -> health_bmhi
- fche -> health_fche
- topsis -> health_topsis
- cdci -> health_cdci
- crhe -> health_crhe
- edrl -> life_edrl
- wrrl -> life_wrrl
- bdrl -> life_bdrl
- gple -> life_gple

新增统一解析方法：
- `requireHealthAlgoColumn(algo)`
- `requireLifeAlgoColumn(algo)`
- `normalizeAlgo(algo)`

外部 algo 必须先经过固定 Map 映射后才得到 SQL 列名；非白名单算法抛出 IllegalArgumentException，在 SQL 构造前被拒绝。

说明：JDBC `?` 参数只能绑定值，不能安全绑定表名/列名等 SQL 标识符。因此本项按审计建议采用“服务端固定标识符白名单”，而不是错误地尝试对列名使用 PreparedStatement 参数。

## 四、扩大复核
没有只修改报告截图中的单一路径，同时修复 HealthAlgoController 内所有由请求 algo 控制的 health_* / life_* 动态 SQL 列名入口，避免攻击者切换 list/stats/life-* 接口绕过整改。

复核结果：
- apply/list/stats 三处健康算法动态列均调用 `requireHealthAlgoColumn`；
- life-apply/life-list/life-stats 三处寿命算法动态列均调用 `requireLifeAlgoColumn`；
- 剩余 `base.get("health_" + algoNames[i])` 只是 Java Map key 访问，且 algoNames 为代码内固定数组，不参与 SQL，不属于 SQL 注入点。

## 六、当前结论
状态：已完成代码整改并通过静态复核。

针对原报告 3.10 所描述的“用户可控 algo 直接进入 SQL 列名”攻击链，当前代码已切断：请求参数不能再产生任意 SQL 标识符，只能选择服务端预定义列名。后续审计复测建议对 apply/list/stats/life-* 接口分别提交正常算法值与包含空格、引号、反引号、逗号、SQL 关键字的恶意 algo，确认恶意值在 SQL 执行前被拒绝。
