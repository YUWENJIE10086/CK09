# 3.15 单项整改记录：SysUserController 批量赋值

## 一、原审计项
- 原报告编号：3.15
- 风险等级：高风险
- 原问题：SysUserController 直接使用 `@RequestBody SysUser` 绑定数据库实体，客户端可提交超出业务预期的实体字段，形成 Mass Assignment / 批量赋值风险。
- 原报告修复方向：使用专用 DTO/Request 对象，只接收业务允许字段，并在服务端显式映射。

## 二、代码核验
涉及文件：
- `Traeppp09/ruoyi-barn/src/main/java/com/barn/system/controller/SysUserController.java`
- `Traeppp09/ruoyi-barn/src/main/java/com/barn/system/entity/SysUser.java`

整改前：
- 新增：`add(@RequestBody SysUser user)`
- 修改：`edit(@RequestBody SysUser user)`

SysUser 数据库实体同时包含 id、deptId、userType、password、status、delFlag、loginIp、loginAt、createdBy、createdAt、updatedBy、updatedAt 等字段。直接反序列化实体意味着客户端 JSON 可尝试绑定这些字段。虽然 edit 手工将 password 置空，但其他服务端维护字段仍暴露在绑定面上。因此原报告 3.15 问题真实存在。

## 三、实际整改
新增：
`Traeppp09/ruoyi-barn/src/main/java/com/barn/system/dto/SysUserRequest.java`

DTO 仅暴露用户管理业务所需字段：
- id（修改时定位对象；新增时不复制到实体）
- deptId
- userName
- nickName
- userType
- email
- phone
- sex
- avatar
- password（仅新增初始密码使用）
- status
- remark

明确不暴露：
- delFlag
- loginIp
- loginAt
- createdBy
- createdAt
- updatedBy
- updatedAt

Controller 的 add/edit 均改为 `@RequestBody SysUserRequest`。

新增 `copyAllowedUserFields(...)`，通过逐字段 setter 白名单复制业务字段，而不是 BeanUtils/反射式整体复制。

### 新增用户
服务端重新创建 `new SysUser()`：
- DTO 的 id 不写入；
- password 单独校验后 BCrypt 编码；
- createdAt/updatedAt 服务端生成；
- delFlag 强制服务端设为 "0"；
- status 无值时服务端默认 "0"。

### 修改用户
- request.id 仅用于定位现有用户；
- 先确认目标存在；
- 创建新的局部 SysUser 更新对象；
- id 取已查询对象的真实 id；
- 仅复制白名单业务字段；
- password 不通过普通 edit 修改；
- updatedAt 由服务端生成；
- 审计/登录/逻辑删除字段无法从请求 DTO 注入。

## 四、静态复核
整改后检查：
- `@RequestBody SysUser user`：0 处；
- add 使用 SysUserRequest：是；
- edit 使用 SysUserRequest：是；
- DTO 含 delFlag/loginIp/loginAt/createdBy/createdAt/updatedBy/updatedAt：全部否；
- delFlag 新增默认值由服务端设置：是；
- password 仍在 DTO 中，但仅 add 显式读取并 BCrypt；edit 的映射函数不复制 password。

因此即使客户端 JSON 额外提交 `delFlag`、`loginIp`、`createdAt` 等字段，也不会绑定到 SysUser 数据库实体。

## 五、边界说明
userType/status 是否允许“谁”修改属于授权/RBAC问题，将在原报告 3.16 中处理。本项解决的是“哪些字段可以进入写入模型”，不以 DTO 替代角色授权。
